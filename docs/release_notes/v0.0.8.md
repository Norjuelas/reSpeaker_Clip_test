# Release 0.0.8

## Overview

Battery state-of-charge accuracy release: direct fuel-gauge SoC reporting,
WiFi (nRF70) fuel-gauge compensation, charge-complete 100% display, cached
storage status when the SD is idle, faster boot with many sessions, and a
more reliable pairing reset.

## Changes

### Battery reporting

- The OLED, BLE Battery Service, `AT+GSTAT`, and `AT+BATT` now report the
  nRF Fuel Gauge's integer SoC estimate directly.
- Removed application-level EMA smoothing, per-poll rate limiting, charging /
  discharging directional clamping, and the 100% display latch. Those display
  layers could accumulate a large lag during charging and then jump after a
  restart.
- Fuel-gauge state persistence remains enabled, so the gauge itself continues
  its voltage/current/temperature estimate across a restart.

### Charge-complete 100% display

- The nRF Fuel Gauge plateaus at ~99% on a full charge (model full vs charger
  CV-termination mismatch). After the EMA/latch layers were removed (see
  Battery reporting above) a full charge showed 99%.
- Re-added a minimal latch: force the display to 100% when the NPM1300 reports
  charge complete while VBUS is present. No EMA / sticky-after-unplug behavior.
  The raw gauge value is still logged as `actual` for calibration.
- Charging with WiFi on may not report complete (the nRF70 load holds the
  charge current above the termination threshold); that case stays below 100%
  and reaches 100% once WiFi auto-offs and the charger terminates.

### WiFi fuel-gauge compensation

- The nRF7002 main VDD (BUCKVBAT) is tied to VBAT upstream of the NPM1300, so
  its radio TX/RX/internal-buck current never passes through the PMIC's IBAT
  sense resistor. `GAUGE_AVG_CURRENT` therefore undercounted discharge (and
  over-counted charge while charging) whenever WiFi was on, so the fuel gauge
  SoC read high during WiFi AP / UDP transfer use.
- `battery.c` now folds a state-keyed WiFi-load estimate into the current fed
  to `nrf_fuel_gauge_process()`, applied as extra discharge in both charge and
  discharge states. A state-transition log line aids calibration:
  `Battery fg: ibat=X mA, wifi_comp=Y mA`.
- Configurable via `CLIP_BATTERY_WIFI_LOAD_COMPENSATION` (on/off),
  `CLIP_BATTERY_WIFI_AP_LOAD_MA` (AP up, no transfer), and
  `CLIP_BATTERY_WIFI_TX_LOAD_MA` (active UDP transfer). Defaults are upper
  bounds that over-compensate safely; trim from
  (total battery current on the VBAT rail − |IBAT|).

### Pairing reset reliability

- `AT+PAIR=reset` now acknowledges after clearing bonds and persisting, then
  erases the SD card and reboots from a background worker. Previously the
  synchronous SD format could time out the BLE client on a card full of
  recordings.

### Storage status when SD is idle-unmounted

- `AT+STORAGE` and `AT+GSTAT` (`free_space`) now report the last-known cached
  capacity/free when the SD is unmounted by the idle power-gate, instead of
  0 / "not mounted". The values survive unmount (free space doesn't change
  while idle), and `AT+STORAGE` adds a `mounted` field (true/false) so the
  caller knows live vs cached. The SD is not woken for status queries,
  preserving the idle power-gate.
- The cache is refreshed right before the SD idle-unmounts (and on mount /
  on mounted status queries), so it reflects post-write values (e.g. after a
  recording) instead of going stale. A transient `fs_statvfs` failure no
  longer zeroes the cache.

### Faster boot with many sessions

- The boot-time untransferred-record check (`display_check_untransferred` →
  `storage_has_unsynced_sessions`) and `AT+LIST` scanned the entire
  REC/<day>/<hour>/<minute>/<session> tree even when only a few session IDs
  were needed (64 for the check, 200 for a LIST page). With thousands of
  sessions this blocked boot for a long time. `scan_session_ids` /
  `scan_bucket_sessions` now stop once `max_ids` are collected — O(64/200)
  instead of O(all). The `max_ids==0` count path still walks all. Behavior
  unchanged (only the first `max_ids` were ever checked).
- The untransferred-recordings indicator (`storage_has_unsynced_sessions`)
  now returns true whenever any session exists, instead of reading each
  session.json to compare synced_files vs file_count. O(1) at boot (scan
  stops at the first session) instead of O(64) reads. Semantic change: the
  indicator shows whenever recordings exist, even if all are fully synced.
